# 巡检记录表 — 字段与协作机制

这是巡检用的一张**建议日志表**：每发出一条照看或请示，就落一行。它负责记住「说过什么、为什么说、用户回没回」。

存储中立——Notion 数据库、飞书多维表格、Airtable、Excel / Google Sheets、CSV、JSON 文件都行，字段语义一致即可。

> 文中示例全部虚构，不含真实用户内容、私人链接或生产资源标识。

---

## 一、三层职责，不要堆进同一张表

状态被拆在三处，各有权威源：

| 层 | 存什么 | 谁是权威 |
| --- | --- | --- |
| **记录表**（多维表格/表格/JSON 均可） | 每一条已决定发出的建议：说了什么、为何、状态、用户回没回、发出后的消息编号 | **待办与日志的权威源**。待办 = 状态为「待响应」的行 |
| **本地运行时状态**（如 `state.json`，不进 Git） | 按**类别**的沉默连击、冷却截止、当日发送计数；活动/位置等缓存；上次运行时间；当晚安静模式 | **冷却与降频的权威源**。不保存单条建议。字段见 [`state-schema.md`](./state-schema.md) |
| **主会话聊天** | 真正发给用户的口语正文；用户的回复和表情 | 发送成功后才有消息编号；对账时回去对照 |

待办只认记录表里的「待响应」，state 不另存一份。state 丢了，只需从零重建冷却/沉默/活动缓存，**不必**从记录表回填单条建议。

页面正文不是必需字段。消息编号正式成列之前，曾有过写在正文里的做法；现在一律回填「消息ID」列。

## 二、10 个业务字段

标题字段的真实名称是**「内容摘要」**（口语里可能简称「摘要」，建表时按真实名写）。

**不存在**独立列「已代办」「取数时间」。这两项是**写入约定**，不是 schema 字段。

| 字段 | 类型 | 必要性与作用 |
| --- | --- | --- |
| **内容摘要** | 标题（title） | 必填。本轮切口的短标题，一行一条建议的可读名称。 |
| **类别** | 单选 | 必填。与 state 的类别计数器对齐。选项只能是：出行、截止、等回复、空档、健康、日记、其他。 |
| **发出时间** | 日期时间（date，可带时刻） | 必填。这条建议对用户发出（或准备发出）的时间。 |
| **状态** | 单选 | 必填。选项只能是：待响应、已响应、已忽略、已冷却。新建时为「待响应」。 |
| **理由** | 长文本 | 内部依据：为何选这个切口、本轮上下文要点、**是否已代办**、对其它待响应行做了哪些对账。不对用户直接展示。 |
| **可选动作** | 长文本 | 这条建议希望发生的下一步，以及「用户不回时，可逆的推荐默认」。常见两段结构：先写「口语正文：…」，再写「推荐默认：…」。 |
| **建议ID** | 自动递增整数 | 存储层在创建时分配，是行级稳定标识。文本里常写成 `PA-<建议ID>`。**不是**写入前可计算的业务去重键。 |
| **消息ID** | 文本 | 主会话把口语正文发出成功后，把返回的消息编号写回这里，用于把后续回复/表情精确对到这一行。未发出成功前应留空，不要编造。 |
| **用户回应** | 长文本 | 对账后填写。文字回应用原话；表情写成「表情：…」。忽略收口时也可在此写明「因挂太久且无引用而收成已忽略」。 |
| **冷却截止时间** | 日期时间（date） | 这一列留着备用；冷却实际记在 state 的 `cooldown_until` 里，按类别而不是按行。 |

存储层还会有系统列（记录 URL、创建时间等），它们不是业务字段，不用建。

### 两项写入约定（别做成列）

- **已代办**：本轮已经动手做了可逆协助时，在**「理由」**等文本里注明，例如「已在任务下留了可逆的提纲评论（已代办）」。不要新增复选框列。
- **取数时间**：各类上下文实际取数的时间，记在**「理由」**等记录文本里，**不塞进发给用户的消息**。不要新增日期列。

## 三、状态流转

```
创建并发出（或先落盘再发出）
        │
        ▼
     待响应  ← 这就是 pending / outbox
        │
        ├─ 用户回话或点表情（有引用则按消息ID 精确匹配；无引用则对最近一条待响应；
        │   对不上就问一句，不乱标）
        │     → 已响应，并填写「用户回应」
        │
        ├─ 大约一两天仍挂着、没有引用、只有空回应或不足以构成有效回复
        │     → 已忽略 或 已冷却（不要永远停在拿不准）
        │
        └─ 同一具体提议被连续三次完全沉默
              → 该【类别】进入约 24 小时冷却（写在 state 里，不靠「冷却截止时间」列）
                 冷却期内换别的切口继续照看，不是整轮静默
```

边界：

- 「忙」「稍后」= 推迟，不计入完全沉默。
- 表情，或一句「好」「知道了」，只说明看见了：标「已响应」，**不等于**否决可逆的下一步，也不要为此空等暗号。
- 需要用户拍板才生效的动作，仍留短暗号（如「挪」「删」「试」）。拿不准就不擅自做。
- 「已响应」不是一切停下：可逆的下一步仍可在后续巡检继续铺。
- 执行前判断「先做还是先问」的分级，见 [`reversible-actions.md`](./reversible-actions.md)（按自身权限换算；沉默不等于授权）。

## 四、一轮巡检里各层何时读写

1. **读 state**：沉默、冷却、降频、活动缓存。
2. **查记录表，先处理漏标。** 列出状态为「待响应」的行，对照主会话里之后的回复和表情（优先用「消息ID」）。该改「已响应」的补改并填「用户回应」；该收成「已忽略 / 已冷却」的收口；对不上先不动。**这一步必须发生在选择新切口之前。**
3. **拉上下文并选一个切口**（选切口的规则不属于本表）。
4. **新增一行**：内容摘要、类别、发出时间、状态=待响应、理由、可选动作；已代办在理由里注明；请示类在可选动作里写推荐默认。建议ID 由存储分配。
5. **把口语正文交给主会话发出**（正文在聊天里，通常同时备份在「可选动作」的口语正文段）。
6. **发送成功后更新「消息ID」**。没有编号就难以可靠对账。
7. **更新 state**：该类别发送计数、沉默连击或冷却截止、活动缓存、上次运行时间。字段见 [`state-schema.md`](./state-schema.md)。

用户在主会话当场回话时，由主会话立即把对应行标为「已响应」；巡检开头的对账只补漏。

## 五、逻辑存储接口（存储中立）

实现时面向这些操作，不要把某一家产品的库 ID 或页面 URL 写进公开提示词——连接信息放在部署侧配置里。

- `list_pending()`：查询状态 = 待响应。这就是待办 / outbox。
- `get_by_suggestion_id(id)`：用自动分配的建议ID 取一行。
- `get_by_message_id(message_id)`：用回写的消息编号精确对账。
- `create_record({内容摘要, 类别, 发出时间, 理由, 可选动作, 状态: "待响应"}) -> 建议ID`：插入一行，接受存储分配的标识。
- `update_message_id(建议ID, 消息ID)`：仅在发送成功后调用，应幂等（同一编号重复写回保持不变）。
- `mark_responded(建议ID, 用户回应)`：状态改为已响应。
- `mark_ignored_or_cooled(建议ID, 说明)`：状态改为已忽略或已冷却，说明可写入「用户回应」或「理由」。
- `set_row_cooldown(建议ID, until)`：**可选**。只有决定把冷却做到行上时才需要，默认不走这条。

去重与重启：

- 建议ID 是行标识，不是业务去重键。同一轮不要为同一切口插两行；选新切口前必须先对账待响应。
- 发送与落盘幂等：先有行、后有消息ID；发送失败时不要伪造消息ID，也不要在对账前重复推同一条待响应。
- 进程重启后：待响应行仍是待办权威源；用消息ID 把聊天里后到的回应补标。本地冷却/沉默若丢失，只会暂时失去降频记忆，不会丢待办。

## 六、示例

下面是一轮巡检之后表里的样子。三行，三种状态，都是虚构的。

### 6.1 总览

为了能横着放下，这里只列关键几列；完整字段见 6.2。

| 内容摘要 | 类别 | 发出时间 | 状态 | 消息ID | 用户回应 |
| --- | --- | --- | --- | --- | --- |
| 周三评审会材料还没起个头 | 截止 | 11-17 10:30 | 待响应 | `msg-20261117-001` | |
| 季度照片要不要挪到周末整理 | 空档 | 11-17 11:30 | 已响应 | `msg-20261117-002` | 挪 |
| 今天步数离目标还差一半 | 健康 | 11-16 20:30 | 已冷却 | `msg-20261116-003` | 表情：👀（连续第三次没实质回应，收成已冷却） |

三行的差别刚好说明了状态怎么走：

- 第一行发出去了，用户还没回，所以是**待响应**——它同时是一条待办。
- 第二行用户回了「挪」，**已响应**，「用户回应」记下原话。注意「已响应」不等于事情办完了，只是这条提议有了回音。
- 第三行连挂两三天、只有个表情，收成**已冷却**，这一类进了 24 小时冷却。不收的话它会一直占着「待响应」，下一轮对账又得重新判一遍。

### 6.2 其中一行的完整字段

| 字段 | 值 |
| --- | --- |
| 内容摘要 | 周三评审会材料还没起个头 |
| 类别 | 截止 |
| 发出时间 | 2026-11-17T10:30:00+08:00 |
| 状态 | 待响应 |
| 理由 | 明天上午评审，材料还是空的。已在该任务下留了三行提纲的评论（已代办）。取数时间：待办 10:28／日程 10:29。 |
| 可选动作 | 口语正文：明天上午评审，材料我先帮你列了三行提纲，你填一下就能用。<br>推荐默认：不回则保留评论，不改任务时间。 |
| 建议ID | 101 |
| 消息ID | msg-20261117-001 |
| 用户回应 | *（待响应时为空）* |
| 冷却截止时间 | *（留空，冷却记在 state 里）* |

注意两处不在列里的信息：

- **已代办** 写在「理由」里，没有单独的列。
- **取数时间** 也写在「理由」里，不进发给用户的消息。

### 6.3 用户回复之后

用户引用 `msg-20261117-001` 回了一句「明早我看」，这一行变成：

| 状态 | 用户回应 | 消息ID |
| --- | --- | --- |
| 已响应 | 明早我看 | `msg-20261117-001`（不变） |

只动「状态」和「用户回应」两列。消息ID 是这一行的锚点，对账时靠它把聊天里的回复找回来，所以任何时候都不改它。

## 七、几个容易写错的地方

- **业务字段是 10 个**，不多不少。
- **标题字段叫「内容摘要」**，不叫「摘要」。
- **「已代办」「取数时间」不是列**，是写入约定：已代办写进「理由」等文本，取数时间同理，且不进用户消息。
- **冷却不在本表**。按类别记在 state 里（`cooldown_until`），「冷却截止时间」这一列留着备用、实际没在用。state 是什么、和本表怎么分工，见 [`state-schema.md`](./state-schema.md)。

## 八、在具体工具里落地

只要满足三条，就能被提示词直接使用：

1. **可按状态筛选**，能筛出所有「待响应」行。
2. **可按时间排序**，能取到最近一条待响应行。
3. **单行可编辑**，能回填「状态」「用户回应」「消息ID」。

参考实现：

- **Notion**：建一个数据库，每个业务字段对应一个属性；`类别`/`状态` 用单选并锁定上面两组枚举；`建议ID` 用自动编号或自动递增。
- **飞书多维表格 / Airtable**：同上，字段类型一一对应；`建议ID` 用自动编号。
- **Excel / Google Sheets / CSV**：一行一条记录，`类别` 与 `状态` 用数据验证限定取值，避免手滑写出变体；`建议ID` 用公式或手工递增。
- **纯 JSON**：数组存记录，字段名沿用上表；适合脚本化巡检，不利于人工回看。

### 示例表头（CSV）

```csv
内容摘要,类别,发出时间,状态,理由,可选动作,建议ID,消息ID,用户回应,冷却截止时间
"示例：提醒下午把材料草稿先起个头",其他,2026-11-17T16:30:00+08:00,待响应,"示例：仍未开始；已留提纲评论（已代办）",示例：口语正文…／推荐默认…,101,,,
```

## 九、接进巡检

1. 按第二节建表，表名随意，例如「Proactive 记录」。
2. 把访问方式（数据库 ID、表格链接、文件路径）放在运行巡检的环境里。
3. 这份文件放在提示词同目录的 `reference/` 下，让助手开启时能读到——它解释字段语义，比让模型猜字段名可靠。
4. 提示词里凡出现「记录表」，都指这张表；换工具时只改访问方式，不改提示词。
5. 另一份存储是 state，字段与用法见 [`state-schema.md`](./state-schema.md)；丢了只影响降频记忆，不影响待办。

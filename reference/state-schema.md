# state — 跨轮记忆

`state.json` 是巡检自己的**跨轮记忆**。它跟记录表不是一回事，两者分工不同，混在一起会出问题。

## 为什么需要它

每轮巡检都是重新醒来，助手不带上一轮的印象。有些事只看单条记录算不出来：

- 这类事我已经说过第三次了，该停了吗？
- 今天已经发了几条，还该不该再发？
- 昨天那轮跑完是什么时候，有没有漏跑？
- 上一次真的把消息发出去了吗，发送通道还活着吗？

这些都要**跨行、跨轮、跨天累计**，翻一遍记录表去数既慢又容易数错。所以有个专门的地方记这些数。

## 和记录表的区别

一句话：**记录表记「每一件事」，state 记「说过几件事」。**

| | 记录表 | state |
| --- | --- | --- |
| 粒度 | 一条建议一行 | 一个类别一个数 |
| 回答的问题 | 这条说了什么、用户回没回 | 这类事我说过几次、还该不该说 |
| 写的时候 | 每发一条写一行 | 每轮读一次、按需要改几个数 |
| 能不能手工回看 | 能，一行行读就是历史 | 不能，它是计数器不是日志 |
| 丢了会怎样 | 待办全丢，必须备份 | 只丢掉降频记忆，待办不受影响 |
| 谁是权威 | 待办与日志的权威源 | 冷却与降频的权威源 |

一句话记法：**记录表是明细账，state 是汇总账。** 明细里查某一笔，汇总里看这个月花了几次。

两边都不能替对方干活：

- state 里不存单条建议。存了就变成两份待办，迟早对不上。
- 记录表里不存累计数。存了就得每轮扫全表去重算，而且「冷却截止时间」那一列本来就会和 state 里的 `cooldown_until` 打架——所以那一列留着不用。

## 字段

### 顶层

| 字段 | 类型 | 作用 | 什么时候写 |
| --- | --- | --- | --- |
| `last_run` | 时间 | 上次巡检是什么时候 | 每轮开跑时 |
| `last_sent_ok` | 时间 | 上次**真的把消息发出去**的时间 | 主会话确认发送成功后 |
| `last_user_response` | 时间 | 用户上次回话是什么时候 | 收口后 |
| `quiet_tonight` | 对象 | 当晚是否安静、到几点为止 | 进入安静模式时 |
| `last_activity` | 对象 | 活动与位置，连同它们的取数时间 | 拉到数据后 |
| `silent_runs` | 整数 | 连续几轮完全没有输出 | 每轮收尾时 |
| `probe` | 对象 | 各依赖上次探活的结果与时间 | 探活后 |
| `counters` | 对象 | 按类别的沉默与冷却 | 发出后、收口后 |

`last_activity` 存数据时要连取数时间一起存——「三小时前的坐标」和「刚才的坐标」在很多切口上不是一回事，光有值没有时间会让人误判。

`quiet_tonight` 是原则 3 里「临睡前」那个判断的依据，不然每轮都会重复劝一遍。`silent_runs` 则用来识别「是不是我自己太久没说话了」，和 `silence_streak` 不是一回事：后者算的是某一类提议，前者算的是整轮。

### counters：按类别

键固定是这七个，和记录表「类别」字段的枚举一一对应：`出行`、`截止`、`等回复`、`空档`、`健康`、`日记`、`其他`。不要临时造新类别，否则统计会断。

每个类别底下一组：

| 字段 | 作用 |
| --- | --- |
| `silence_streak` | 这条具体提议被连续完全沉默了几次 |
| `cooldown_until` | 该类冷却到什么时候；空表示没在冷却 |
| `daily_cap` | 这类事一天最多发几条 |
| `daily_sent_date` | 下面那个计数属于哪一天 |
| `daily_sent_count` | 那天已经发了几条 |

`daily_sent_date` 和 `daily_sent_count` 要成对看：换了一天，计数先归零再累加。只看计数不看日期，会把昨天的账记到今天头上。

## 示例

拿记录表那三行当背景，看同一时刻 state 里是什么样。

### 记录表里的三行

| 内容摘要 | 类别 | 状态 | 用户回应 |
| --- | --- | --- | --- |
| 周三评审会材料还没起个头 | 截止 | 待响应 | |
| 季度照片要不要挪到周末整理 | 空档 | 已响应 | 挪 |
| 今天步数离目标还差一半 | 健康 | 已冷却 | 表情：👀 |

### 同一时刻的 state

```json
{
  "last_run": "2026-11-17T11:30:00+08:00",
  "last_sent_ok": "2026-11-17T11:30:05+08:00",
  "last_user_response": "2026-11-17T11:42:00+08:00",
  "quiet_tonight": null,
  "last_activity": {
    "steps": 4200,
    "fetched_at": "2026-11-17T11:29:00+08:00"
  },
  "silent_runs": 0,
  "probe": {
    "record_table": { "at": "2026-11-17T11:29:00+08:00", "result": "ok" }
  },
  "counters": {
    "截止": {
      "silence_streak": 0,
      "cooldown_until": null,
      "daily_cap": 3,
      "daily_sent_date": "2026-11-17",
      "daily_sent_count": 1
    },
    "空档": {
      "silence_streak": 0,
      "cooldown_until": null,
      "daily_cap": 2,
      "daily_sent_date": "2026-11-17",
      "daily_sent_count": 1
    },
    "健康": {
      "silence_streak": 3,
      "cooldown_until": "2026-11-18T10:30:00+08:00",
      "daily_cap": 1,
      "daily_sent_date": "2026-11-16",
      "daily_sent_count": 1
    }
  }
}
```

### 对照着看

| 记录表里看到的 | state 里对应的 |
| --- | --- |
| 「截止」那一行是待响应 | `counters.截止.daily_sent_count` = 1，今天已经发过一条 |
| 「空档」那行用户回了「挪」 | `last_user_response` 更新到 11:42；空档的 `silence_streak` 归零 |
| 「健康」那行已冷却 | `counters.健康.silence_streak` = 3，`cooldown_until` 指到明天 10:30 |

三行的关键差别在这里：

- **看「健康」**：记录表里它只是一行，看上去没什么特别。但 state 里 `silence_streak` 攒到了 3，所以这一类进了 24 小时冷却。**这个数只在 state 里有。**（这 3 次是跨轮次累积的，表里只截了三行示例，前面那两轮没画出来。）
- **看「空档」**：用户回了「挪」，`silence_streak` 清零。如果不清，下次同类提议一来就少一次容错。
- **看 `probe`**：记录表里完全看不到这个。它是「这张表还读得通」的证据，只在 state 里。
- **看 `daily_sent_date`**：健康那一格是 `11-16`，另外两类是 `11-17`。同一天里发过的才算进今天的额度，跨天了要重新计。

### 反过来，state 里没有的

- 说不出「周三评审会材料」这条具体是什么事——那在记录表的「内容摘要」里。
- 说不出用户当时回了哪句话——那在「用户回应」里。
- 说不出这条建议是几点发的——那在「发出时间」里。

这就是「汇总账不记明细」的意思：state 只看得出「截止类今天发了 1 条」，看不出那 1 条讲的是什么。

## 一轮里怎么读写

1. **开跑读**：沉默连击、冷却、今天已发几条、上次运行时间、上次发送时间、当晚是否安静。
2. **发出后写**：`last_run`、`daily_sent_count` 加一（`daily_sent_date` 不是今天就先归零）、`last_sent_ok`（只在确认送达后）。
3. **收口后写**：`silence_streak` 加减、`cooldown_until`、`last_user_response`。
4. **拉到数据写**：`last_activity`，连取数时间一起。
5. **每轮收尾写**：有输出就清零 `silent_runs`，没输出就加一。

顺序有个讲究：**`last_sent_ok` 要等发送确认后才能写**。没确认就写，等于谎报发送通道还活着；下一轮探活时会被这个假信号骗过去。

## 丢了怎么办

直接重建一份空的就行，不需要从记录表回填。

代价只有一个：暂时失去降频记忆。表现为可能把已经冷却过的事再说一遍，或者当天多发一条。**待办不会丢**，因为待办在记录表里。

## 为什么不进版本库

它是这台机器上的运行时数据，每轮都在变，和代码不是一回事。放进 Git 会有两个问题：每次提交都是噪音，而且换机器时旧计数会被带过去，与新环境对不上。

`state.json` 已经在 `.gitignore` 里。连接信息（库 ID、表格链接、文件路径）同样不进库——它记的是「想连什么」，这份记的是「跑到哪儿了」，两份都不该跟着仓库走。
